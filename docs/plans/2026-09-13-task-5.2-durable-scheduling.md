# Task 5.2 — Durable scheduling and delivery

Local behavioral proof for **P5.2** on migration chain **`0000`–`0009` only** (no
`0010`/`0011`). Physical PWA/iOS notification observation remains **P7**.

## Deployed worker topology (code + runbook)

| Layer | Mechanism | Lock / dedupe |
|-------|-----------|---------------|
| **Trigger** | Coolify scheduled task `kairo-jobs-tick` (`* * * * *`) runs `fetch('http://127.0.0.1:3000/api/v1/jobs/tick', … Bearer CRON_SECRET …)` **inside the app container** | Bearer `CRON_SECRET` or `x-cron-secret`; fails closed in production when unset |
| **Orchestration** | `POST /api/v1/jobs/tick` → `startSchedulerRun` → `materializeRoutines` → `computeNotificationJobs` → `deliverDueNotificationJobs` → `succeedSchedulerRun` → `pruneSchedulerRuns` | Each failed stage calls `failSchedulerRun`; HTTP 500, no silent partial success |
| **Routine materialization** | `materializeRoutines` in a DB transaction | `pg_try_advisory_xact_lock(8947231)` — second concurrent tick skips work (`processed: 0`) |
| **Notification compute** | `computeNotificationJobs` in a DB transaction | `pg_try_advisory_xact_lock(8947232)`; unique `dedup_key` index |
| **Delivery** | `deliverDueNotificationJobs` claims due rows | `FOR UPDATE SKIP LOCKED` + 5‑minute claim lease + heartbeat; max 5 attempts |
| **Readiness** | `GET /api/health` | `checks.migrate`, `checks.db`, `checks.scheduler` (+ `schedulerLagSeconds`) |

There is **no** in-process `node-cron` worker in this repository. Page-load and
app-open paths do **not** run the scheduler (ADR-004 “never page-load checks”).

### ADR-004 contract resolution (documentation only — topology unchanged)

**Historical ADR text** described a dedicated in-container `node-cron`-style worker
with a single advisory-lock lease.

**Actual production path (since 2026-07-24, `docs/DEPLOYMENT.md`):** Coolify cron
invokes the authenticated HTTP tick every minute. Stages still use Postgres advisory
locks and row-level claiming; reliability does not depend on a separate Node cron
process.

**Decision (Task 5.2):** Treat **Coolify scheduled HTTP tick** as the binding
scheduler implementation. ADR-004 is updated to match. Coolify remains the
fallback-of-record if an future in-process worker were added — not deployed today.

## Health and alert thresholds (from code policy)

Source: `getSchedulerHealth` (`scheduler-runs.ts`), `GET /api/health` (`health/route.ts`),
`DEPLOYMENT.md` container health section.

| Signal | Threshold | `/api/health` | Operator action |
|--------|-----------|---------------|-----------------|
| Migration incomplete | any apply failure | `checks.migrate: fail`, HTTP **503** | Stop deploy; restore from predeploy backup (runbook §Production) |
| Database unreachable | `SELECT 1` fails | `checks.db: fail`, HTTP **503** | Check Postgres / credentials / network |
| Scheduler unconfigured | `CRON_SECRET` unset in **production** | `checks.scheduler: unconfigured`, HTTP **503** | Set secret + verify Coolify task uses same value |
| Scheduler warming | no finished run yet, process age ≤ **5 min** | `checks.scheduler: warming`, HTTP **200** | Wait for first successful tick after deploy |
| Scheduler lagging | latest **success** finished > **5 min** ago, or no success after warm-up | `checks.scheduler: lagging`, HTTP **503** | Inspect Coolify task executions; fix 401/500 ticks |
| Scheduler failed | newest **completed** run is `failed` after last success | `checks.scheduler: failed`, HTTP **503** | Read `scheduler_runs.last_error`; fix root stage |
| Tick HTTP failure | tick returns 500 | Not in health JSON — use Coolify execution log | Same as failed run row |
| Repeated job failure | `notification_jobs` stuck in `retry` / `expired` with `last_error` | No dedicated metric (no telemetry sink on main) | SQL spot-check per user; P7 for device-side |
| Backup failure | — | **Not** exposed in `/api/health` | Coolify DB backup UI / off-host retention (B6) |
| Elevated request errors | — | **Not** on main (parked `feat/client-error-sink` / `0011`) | External HTTP monitor on `/api/health` + app logs |

Docker `HEALTHCHECK` uses the same `/api/health` 503 semantics (5‑minute scheduler
lag, production unconfigured cron).
